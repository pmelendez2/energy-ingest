# Checking Historical Date Ranges Through the API

- **Purpose:** Describe the first read-only API for checking whether past usage data needs to be retrieved again.
- **Intended Audience:** Energy Ingest and Home Assistant developers.

## What this feature does

When a utility supplies a correction or a late reading, an application may
need to refresh usage data it requested earlier. Energy Ingest now provides
an authenticated API that checks several date ranges together. The API uses
the same Rust reading resolver and historical reconciliation planner used by
Energy Ingest itself. Home Assistant does not choose between conflicting
readings.

This API **does not write to Home Assistant**, calculate a bill, or decide
that missing readings represent zero usage. It does not change the database.

## Definitions

| Term | Meaning |
| --- | --- |
| **Date range** | A period of time being checked. Customers select calendar dates; the API internally uses exact UTC start and end times. |
| **Reading** | An electricity or natural gas observation supplied by the utility. |
| **Validated** | Energy Ingest can select the available readings without a known conflict. This does not mean that every hour or day has a reading. |
| **Fingerprint** | A digital identifier for the selected readings in one date range. It changes when the selected content changes. |
| **Previous fingerprint** | The identifier remembered by an application after an earlier successful check. It is not proof that old readings were correct. |
| **Refresh** | Obtain the latest validated readings again. |
| **Blocked** | Do not use this result to update historical usage: readings are absent or cannot be safely resolved. |

## Example

An application last checked October 1–7, 2026. Later, the utility supplies a
correction for October 3. On the next check, Energy Ingest computes new
fingerprints from the readings it has actually accepted. The application sees
`refresh` for any affected date range and can request validated readings again.

An unchanged fingerprint produces `unchanged`, while missing or conflicting
observations produce `blocked`. The API does not infer missing values.

## API version 1: request and response

**Versioning:** The `/v1/` path defines version 1 of both the request
and response formats, their fields, validation, and behavior. There is no
separate contract version or version field in the response. Compatible
changes may stay within `/v1/`; incompatible changes require a new API
version.

**Route:** `POST /v1/meters/{id}/history/plan` with the same bearer-token
authentication as other Energy Ingest API endpoints.

The body provides requested ranges and, optionally, previous fingerprints.
Omit `previous` for a first check. The example below shows two dates; the
internal UTC timestamps are generated by an application, not entered by the
customer.

```json
{
  "ranges": [
    {
      "start": "2026-10-01T00:00:00Z",
      "end": "2026-10-02T00:00:00Z"
    }
  ]
}
```

An illustrative response:

```json
{
  "physical_meter_id": 1,
  "ranges": [
    {
      "start": "2026-10-01T00:00:00Z",
      "end": "2026-10-02T00:00:00Z",
      "action": "refresh",
      "current_fingerprint": "<server-generated fingerprint>"
    }
  ]
}
```

Save a successful `current_fingerprint` together with its exact start and
end. On a later request, supply the complete list using `previous`, with
`start`, `end`, and `fingerprint` for every requested range. The previous
and current partitions must match; if they do not, the request is rejected
instead of silently skipping any history.

### Limits and rules

- Each request covers **1–12 nonoverlapping date ranges**. Each range can
  cover no more than 31 days, measured in UTC. Both boundaries must use the
  `YYYY-MM-DDTHH:MM:SSZ` format; the end boundary is excluded.
- Duplicate, overlapping, invalid, or changed partitions are rejected.
- A range with no observations is `blocked`, not zero consumption. An
  unresolved range is also `blocked` and has no fingerprint.
- If a range exceeds the existing candidate-reading limit, the API returns
  HTTP 413. Split it into smaller ranges before retrying.
- Only fingerprints calculated from **accepted data by Energy Ingest** are
  authoritative. Previous fingerprints supplied by an application are
  compared, but do not determine validity.

## What remains to implement

This is a bounded read-only comparison, **not a persistent synchronization
service**. The individual date ranges are queried in sequence rather than
inside one database snapshot. An import concurrent with a request could
change results between ranges. The API does not discover which dates need
checking, issue a durable change cursor, or apply corrections to Home
Assistant Recorder. Those safeguards are required before enabling automatic
historical updates.
